# V13.27.1.28-32 Research Renewal Design

## Status

- Parent program: `automatic_strategy_to_demo_v26_2aff44adf84d039c`
- V27 disposition: immutable `completed_zero_qualified_candidates`; no rerun or rescue
- Human gate: exact immutable Release hash approval only

## Decision

Two implementation routes were considered.

1. **Extend the existing candidate-neutral research factory.** Add small versioned contracts and a V28-V32 orchestrator on top of the existing `CandidateAdapter`, policy objects, data gates, Program ledger, and immutable Release boundary.
2. **Build a separate V28 monolithic runner.** This is initially faster, but duplicates formal-validation, capacity, statistics, and Release logic and would create a second source of truth.

Route 1 is selected. It preserves the V19-V27 evidence chain, keeps Formal Validation free of S01-specific imports, and lets a second synthetic candidate prove that the core is reusable. The main risk is stricter contract plumbing; focused tests and versioned policy hashes mitigate it.

## Architecture

### V28 data contracts

- `causal_eligibility_window_v1` freezes field availability, required lookback, and the first/last eligible signal timestamp before candidate creation.
- Every raw event receives exactly one disposition. Conservation requires raw count to equal eligible plus explicit exclusions.
- A seven-layer readiness model separates signal, ranking, capacity, prefilter, formal, release, and Demo requirements.
- `benchmark_comparability_contract_v1` proves capital, universe, timing, direction, cost, concurrency, and capacity comparability. Non-comparable benchmarks are diagnostic only.

### V29 candidate contracts

- `directional_event_v2`, `pair_relative_value_v1`, and `cross_sectional_portfolio_v1` use separate validators and gate semantics.
- Candidate identities are created only after data readiness and novelty checks.
- Threshold-only variants, renamed failures, post-result symbol filtering, and unavailable same-exchange inputs are rejected.

### V30 bounded research

- The Program has at most two campaigns, six families per campaign, two initial variants per family, four formal candidates per campaign, and the frozen backtest budgets from the approved prompt.
- Failed identities remain archived. Each family may consume one preregistered structural revision only when the mechanism changes.
- Formal and research classifications are explicit; unavailable statistics remain unavailable.

### V31 OKX confirmation

- Same-exchange USDT-SWAP evidence is preferred.
- Cross-exchange portability is allowed only through a frozen audit with no threshold changes.
- A failed portability audit terminates as `blocked_okx_portability`.

### V32 Release boundary

- At most three immutable releases per campaign.
- Generated releases are always `approved=false`; Demo ARM and order counts remain zero.
- The orchestrator stops at `blocked_waiting_exact_release_approval` and emits a Markdown/JSON approval request containing the exact hash.
- No Release path terminates as `completed_zero_qualified_candidates` without importing or arming Demo.

## Data Flow

1. Verify merged V26/V27 baseline and freeze policy hashes.
2. Build readiness layers and causal eligibility windows.
3. Register novel hypothesis families and candidate specifications.
4. Run strategy-type-specific prefilters under the frozen budget.
5. Route qualified candidates to the generic formal core through `CandidateAdapter`.
6. Run same-exchange or preregistered portability confirmation.
7. Either emit immutable Release approval evidence or close with a zero-qualified terminal.

## Failure Handling

- Missing/uncausal fields fail before candidate identity creation.
- Event conservation failures are `implementation_invalid`.
- Formal data gaps are `blocked_formal_data`; OKX gaps and portability failures remain distinct.
- Budget exhaustion never forces a pass.
- No failure path mutates V27 evidence, lowers a gate, reads Locked OOS opportunistically, or enables Demo/Live execution.

## Verification

- A second synthetic adapter verifies candidate-neutral formal-core imports and execution.
- Targeted research/formal/statistical suites, then full Quant tests.
- Console tests only if the immutable Release/import boundary changes.
- Compile, config validation, safety scan, diff check, artifact hash audit, and secret scan.
