# AlphaPilot V13.27.1.34C Public Data Scheduler Design

## Status

Approved by the user's request to proceed with the V34C step after the V34B
closeout. This design keeps the previously stated data-only boundary.

## Goal

Turn the V34B resumable one-shot public collector into an auditable long-running
data service. V34C schedules only due public-data work, repairs observable
collection gaps, records stream freshness and quality, and resumes safely after
shutdown, network failure, or process interruption.

V34C does not generate candidates, run Formal validation, read Locked OOS,
create a Release, approve a strategy, arm Demo, access a private account, or
create an order.

## Chosen Approach

Use a hybrid scheduler built around a deterministic `run_due_cycle` core:

1. A versioned policy object defines each stream cadence and retry behavior.
2. An atomic scheduler-state file records attempts, successes, due times,
   backoff, and incomplete work.
3. A non-blocking process lock prevents overlapping cycles.
4. Each cycle runs only due streams and reuses the V34B normalization,
   provenance, immutable-write, and checkpoint contracts.
5. A CLI supports bounded `--once` execution and an explicit `--loop` mode.
6. The same one-cycle command can later be invoked by Windows Task Scheduler
   without coupling the library to Windows.

This separates scheduling from collection. A scheduler failure cannot rewrite
historical data, and collection remains testable without sleeping or starting a
background process.

## Alternatives Rejected

- **Windows Task Scheduler only:** robust across login and reboot, but hard to
  test portably and insufficient as the sole source of collection state.
- **Always-on Python daemon only:** simple at runtime, but process death and
  restart behavior would be implicit and harder to audit.
- **Run the complete V34B snapshot every few minutes:** rejected because it
  would repeatedly fetch slow-moving metadata and recent funding history,
  producing unnecessary immutable artifacts and public API load.

## Components

### Collection Policy

`OkxPublicCollectionPolicy` is immutable, versioned, hashable, and validates a
bounded cadence for every task. Initial defaults are:

- market snapshots: 5 minutes;
- current funding and open interest: 15 minutes;
- instrument state: 1 hour;
- realized funding increment check: 1 hour;
- product metadata PIT snapshot: 24 hours;
- quality report: 15 minutes.

The policy includes retry backoff, maximum consecutive failures, stream enable
flags, bounded instruments, and a policy hash. Policy changes create new
scheduler evidence; they do not rewrite old state.

### Scheduler State And Lock

The scheduler writes one atomic state document under the existing warehouse
checkpoint root. Each task stores:

- `lastAttemptAt`, `lastSuccessAt`, and `nextDueAt`;
- `status`, `consecutiveFailures`, and a bounded last-error summary;
- latest artifact path and SHA-256;
- latest source timestamp and observed row count.

A process lock is acquired atomically. If another healthy cycle owns the lock,
the new invocation exits with `already_running` and performs no network work.
Stale locks are never silently stolen; an explicit bounded timeout and owner
audit are required.

### Incremental Public Collection

V34C adds a focused incremental collector rather than expanding the V34B class.
It shares public normalization helpers and layout primitives but writes V34C
content-addressed artifacts and append-only indexes.

- PIT metadata is observed only when due. No pre-V34B product state is inferred.
- Funding writes only unseen funding timestamps per instrument. Existing V34B
  rows seed the high-water mark and remain byte-identical.
- Snapshot streams write one immutable observation per due cycle. Identical
  payloads may be referenced again without duplicating bytes.
- Every record keeps `retrievedAt`, source endpoint, source-response hash, and
  causal availability fields.

## Gap Repair Semantics

V34C repairs only gaps that can be observed from the public source and local
ledger:

- missing scheduled cycles are recorded as collection gaps;
- restart triggers the oldest due task first within a bounded catch-up budget;
- funding high-water marks permit incremental recovery of newly published rows;
- current-state streams are never backfilled with fabricated historical state;
- API or budget exhaustion leaves the task overdue and checkpointed for retry.

No gap repair mutates a frozen V34A or V34B artifact.

## Data Quality Monitor

Each quality cycle emits immutable JSON and Markdown summaries containing:

- task freshness and overdue duration;
- success, failure, and retry counts;
- row counts, duplicate keys, null required fields, and monotonic timestamps;
- source-hash and causal-availability completeness;
- funding interval anomalies and stream timestamp lag;
- PIT metadata continuity and instrument-state changes;
- disk usage and latest artifact hashes;
- explicit `healthy`, `warning`, `degraded`, or `blocked` status with reasons.

Quality status is evidence, not a strategy gate. Missing or unavailable fields
remain explicit and are not converted to passing values.

## Runtime And Recovery

`--once` runs one bounded due cycle and exits. `--loop` repeats cycles using a
monotonic wait, handles Ctrl+C by finishing the current atomic write, and exits
cleanly. Network errors use bounded exponential backoff. A restart loads the
state, verifies referenced artifacts, and continues overdue work.

V34C will provide launcher examples but will not register an operating-system
scheduled task automatically.

## Evidence And Program Integration

Every cycle produces a receipt and updates a compact append-only cycle ledger.
The V33 program records a data-foundation extension reference and the latest
quality status. All research and trading side-effect counters remain zero.

Authoritative V34C closeout evidence includes:

- policy and policy hash;
- scheduler-state snapshot and cycle ledger;
- incremental-data manifest;
- quality JSON and Markdown reports;
- restart/resume and idempotency audit;
- V34A/V34B artifact integrity audit;
- zero-side-effect audit.

## Failure Semantics

- Invalid policy or missing registered base snapshot: fail closed before work.
- Active process lock: report `already_running`, no network request.
- Network/rate-limit failure: preserve state, apply bounded backoff, retry later.
- Artifact hash mismatch: mark `blocked`, do not overwrite or continue that task.
- Quality warning: continue unaffected public streams and report the warning.
- Quality block: stop snapshot publication for the affected stream only.
- Pause request: finish the current atomic write, persist state, and exit.

## Verification

Implementation is test-first. Contract tests cover due-task selection, policy
hashing, lock exclusion, restart resume, backoff, funding high-water marks,
content deduplication, PIT anti-backfill, quality classification, bounded error
records, immutable V34A/V34B hashes, zero research/trading side effects, and
CLI one-cycle behavior.

A real bounded BTC/ETH/SOL public-data pilot must run at least two cycles with a
synthetic clock advance, proving that the second cycle executes only newly due
tasks. Full repository tests, compileall, configuration validation, safety
scans, and Git whitespace checks must pass before commit, tag, and push.
