# V13.27.1.26-31 Automatic Strategy to OKX Demo Master Workflow

## Objective

Execute the approved V26-V31 research-to-Demo workflow from the immutable V25 baseline. Preserve causal/PIT evidence, bounded research budgets, one-shot formal validation, immutable releases, and the exact-release human approval gate.

## Governing Decisions

- `targetRGateMode` remains advisory. Economic gates remain hard; no result-driven gate relaxation is allowed.
- V26 is a read-only semantic audit. It may not read PnL, exits, formal results, or Locked OOS data.
- The frozen V25 candidate does not uniquely define `eventExtremeResidualZ` or `recoverySizeZ`: its executable entry is an EMA20/EMA80 trend failure and EMA20 reversal. Choosing residual/recovery formulas would create a new hypothesis. V26 must therefore close the v2 replay path and route to V27.
- Formal validation core stays candidate-neutral. Candidate-specific behavior enters only through a versioned adapter and policy objects.
- Zero survivors and data-blocked routes are valid, fully packaged terminal outcomes. A pass is never manufactured.
- V30 may prepare an immutable Demo Release and exact hash approval request. V31 may not import, approve, ARM, scan, or order without explicit approval of that exact Release hash.
- No API credential persistence, Withdraw integration, Live trading, automatic approval, or automatic ARM is permitted.

## Reliability Supplements

1. Every stage writes a transaction-style checkpoint before advancing the program state.
2. Resume logic validates artifact hashes and stage identity before reusing output.
3. Economic-read counters are explicit and must remain zero for V26.
4. Candidate creation requires a data-readiness certificate before a Candidate ID is admitted.
5. Ranking contracts use semantic slots (`primaryEventSeverity`, `confirmationStrength`, `liquidity30d`, `instrumentId`) and candidate-owned derivations; formal core cannot import candidate modules.
6. Artifact paths are derived from `programId`, `campaignId`, and `candidateId`; no S01 or current-candidate fallback is allowed.
7. A second synthetic candidate fixture proves core reuse and prevents accidental S01 coupling.
8. Result reading is separated from execution and remains one-shot, append-only, and auditable.

## Implementation Sequence

### Phase 1 - V26 Semantic Closure

1. Add failing tests for the generic ranking contract, registry, evidence certificate, and second synthetic candidate fixture.
2. Add failing tests for the V26 sidecar, derivation audit, economic-read counters, immutable v2 closure, and V27 route.
3. Implement only enough code to satisfy those contracts.
4. Run V26 once and freeze the audit artifacts under `reports/automatic_strategy_to_demo/<programId>/v26/`.
5. Verify formal attempts, claims, results, result reads, and Locked OOS reads all remain zero.

### Phase 2 - V27 Bounded Candidate Factory

1. Register candidate-neutral directional-event families with causal field semantics and PIT availability.
2. Reject candidates before identity creation when semantic coverage, capacity coverage, or PIT coverage fails.
3. Generate at most 16 candidates, two per family, with one core setup each.
4. Certify adapter parity, Freqtrade translation parity, ranking coverage, PIT safety, and synthetic-fixture reuse.
5. Run frozen prefilter gates with one survivor per family and no more than six formal candidates.

### Phase 3 - V28 Formal Validation

1. Freeze comparison panel, policies, implementation commit, preregistration, future OOS identity, and remote commit identity in order.
2. Run each admitted candidate exactly once with the existing five-fold purged/embargoed split and cost stress.
3. Read each result once; archive failures permanently and keep zero-survivor output legal.
4. Do not relax gates or mutate a candidate after result access.

### Phase 4 - V29 Confirmatory Data

1. Prefer same-exchange OKX historical data with frozen PIT/provenance manifests.
2. Use portability only when OKX history is insufficient and only under a pre-frozen portability policy.
3. Preserve candidate, strategy, exit, risk, cost, split, benchmark, and gate identities.

### Phase 5 - V30/V31 Demo Cutover

1. Build no more than three immutable Release bundles per campaign.
2. Import as unapproved `demo_waiting_approval` records and emit exact Release/risk hashes.
3. Stop at `blocked_waiting_exact_release_approval` unless the user explicitly approves the exact hash.
4. After approval only, append approval evidence, use authenticated OKX Demo identity, ARM Demo only, run one normal scan, and keep engineering smoke isolated from strategy evidence.
